# Рішення та компроміси

## Потік

```
Helpdesk ──POST /webhooks/helpdesk──▶ app ──INSERT ON CONFLICT──▶ tickets (Postgres)
                                                                     │  status = new
                         worker: claim (FOR UPDATE SKIP LOCKED, lease) ◀──┘
                         ├─ KB search (BM25)
                         ├─ global rate limit (60/хв, Postgres)
                         └─ Claude → draft_ready
Оператор (/operator) ── approve (атомарний draft_ready→approved) / reject
                         worker: claim approved → POST reply_url + Idempotency-Key → sent
```

## Вимоги → як закрито

| Вимога | Рішення |
|---|---|
| Вебхук ≤ 2 с | Обробник робить лише один `INSERT … ON CONFLICT` (~мс) і відповідає `202`. Уся повільна робота — у воркері. Бюджет 1.5 с: якщо БД не встигла — явний `503`, щоб хелпдеск повторив. |
| Дублікати, у т.ч. одночасні | `UNIQUE(event_id)` + `ON CONFLICT DO UPDATE SET received_count += 1`. Гонку вирішує сам Postgres; повтор отримує `200 duplicate`. Тест: 25 паралельних копій → 1 тікет. |
| Не втрачати звернення, піки 500/10 хв | Звернення одразу в Postgres (durable). Таблиця `tickets` — це і є черга: окремий брокер не потрібен при такому навантаженні. 500/10 хв = 50/хв < ліміту 60/хв, тож черга не росте безкінечно; LLM 5–30 с × 60/хв ≈ до 30 паралельних викликів — `LLM_CONCURRENCY=30`. |
| Падіння воркера | Рядок захоплюється з lease (`lease_id`, `lease_until`). Протермінований lease підхоплює інший воркер. Результат пишеться лише `WHERE lease_id = мій`, тож «зомбі»-воркер не перезапише новішого власника. |
| 60 запитів/хв на весь сервіс | Sliding window у таблиці `llm_calls` під `pg_advisory_xact_lock` — ліміт спільний для будь-якої кількості процесів/реплік. Дозвіл бере кожен *запит* до провайдера, включно з ретраями та запитом у режимі без ключа. Ретраї SDK вимкнено (`max_retries=0`), щоб вони не обходили ліміт. |
| Помилки LLM | 429/5xx/529/таймаут/мережа → повтор з експоненційним backoff (до `GEN_MAX_ATTEMPTS`), далі `gen_failed` з кнопкою «Повторити» в UI. 4xx (крім 429) і відмова моделі → одразу `gen_failed`. |
| Режим без API-ключа | Запит до `api.anthropic.com` іде реально (з плейсхолдер-ключем → 401), відповідь ігнорується, повертається статична чернетка (з посиланнями на знайдені статті) із затримкою 5–30 с від початку виклику. Далі все однаково; у UI позначка `stub`. |
| Хелпдеск 5xx / не відповідає | Повтор з backoff до `SEND_MAX_ATTEMPTS`, далі `send_failed` + ручний повтор. |
| Клієнт не отримує відповідь двічі | Таймаут неоднозначний (відповідь могла створитися), тому ретраїмо, але з тим самим `Idempotency-Key` (UUID на тікет), за яким хелпдеск дедуплікує. Локально: відправляє лише власник lease; підтвердження — атомарний перехід `draft_ready → approved`, подвійний клік дає «конфлікт», а не другу відправку. Мок навмисно повертає 503 і «повільні успіхи» (зберіг, але відповів за 15 с > таймауту 10 с) — на `/mock-helpdesk/replies` видно, що дублікатів 0, хоча запитів з одним ключем буває кілька. |

## Чому так

* **Postgres як черга, а не Redis/Celery.** Вимога «не втрачати» + PostgreSQL уже в стеку. `SKIP LOCKED` дає конкурентних споживачів без брокера; менше рухомих частин — менше способів втратити повідомлення між системами (немає dual-write «БД + брокер»).
* **BM25 у пам'яті замість векторів.** 9 статей; детерміновано, без зовнішніх викликів (ембеддинги з'їдали б той самий ліміт), багатомовні `keywords` + префіксний стемер покривають укр/рус/англ. Для великої бази — pgvector.
* **Модель:** `claude-opus-5-5` з `effort: low` (короткі відповіді за статтями; змінюється через `LLM_MODEL`/`LLM_EFFORT`). Увімкнено server-side `fallbacks: "default"` — якщо класифікатор безпеки відмовить, API сам перезапустить запит на рекомендованій fallback-моделі.
* **Оператор може редагувати чернетку** перед підтвердженням — надсилається саме підтверджений текст (`final_message`).
* **Мок хелпдеску вбудований** у той самий сервіс (`/mock-helpdesk/...`); `reply_url` з хостом `helpdesk.example.com` (`MOCK_HELPDESK_HOSTS`) перенаправляється на нього. Реальні URL ідуть як є.

## Безпека

* `WEBHOOK_SECRET` — заголовок `X-Webhook-Secret` (constant-time порівняння). У реальному хелпдеску — HMAC-підпис тіла.
* `OPERATOR_PASSWORD` — Basic auth на `/operator` і `/api`.
* `REPLY_URL_ALLOWED_HOSTS` — allowlist для `reply_url` (інакше вебхук може змусити сервіс робити запити на довільні адреси — SSRF).
* Текст звернення передається в LLM всередині тегів як дані; чернетку завжди перевіряє людина.

## Що б зробив далі

* Alembic-міграції замість ідемпотентного `schema.sql`.
* LISTEN/NOTIFY замість поллінгу раз на секунду.
* Метрики (довжина черги, латентність, частка stub/failed) і алерти.
* Пріоритизація черги (VIP, вік звернення), SLA-таймери.
* Кілька повідомлень в одному тікеті — зараз кожна подія = окреме звернення.
