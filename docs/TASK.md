# Завдання (оригінальний опис)

Сервіс обробляє звернення в підтримку: готує чернетку відповіді для оператора за допомогою LLM.

1. **Отримання:** Хелпдеск надсилає нове звернення на вебхук.
2. **Генерація:** Сервіс знаходить релевантні статті в базі знань і генерує чернетку відповіді з посиланнями на них.
3. **Модерація:** Оператор у веб-інтерфейсі бачить список звернень із чернетками та може підтвердити або відхилити їх.
4. **Надсилання:** Підтверджена відповідь надсилається клієнту через API хелпдеску.

Інтерфейс базовий. Базу знань (5–10 коротких статей про вигаданий продукт) згенеровано AI.

## Хелпдеск (мок)
* Вебхук: `POST /webhooks/helpdesk`; хелпдеск чекає ≤ 2 с, інакше повторює доставку.
* Та сама подія може прийти кілька разів, зокрема одночасно.
* Кілька звернень на хвилину, у піках — до 500 за 10 хвилин. Звернення не можна втрачати.

```json
{
  "event_id": "evt_8f2a",
  "ticket_id": "T-1042",
  "customer_email": "user@example.com",
  "message": "Не можу експортувати звіт у PDF",
  "reply_url": "https://helpdesk.example.com/tickets/T-1042/replies"
}
```

Відповідь клієнту: `POST <reply_url>` з `{"ticket_id": "...", "message": "..."}` → `201 Created`.
Хелпдеск іноді повертає 5xx або не відповідає вчасно. Клієнт не повинен отримати ту саму відповідь двічі.

`/health` → `200 OK`.

## LLM
* Провайдер і модель на вибір; виклик 5–30 с; ліміт 60 запитів/хв на весь сервіс.
* Без API-ключа: усе одно реальний запит до провайдера, а замість відповіді — статична із затримкою 5–30 с.

## Стек
Python (FastAPI), PostgreSQL, `docker compose up`.
